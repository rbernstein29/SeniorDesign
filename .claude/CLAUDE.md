# Aegis — Claude Project Instructions

## Project Overview

Aegis is a multi-tenant vulnerability scanning and penetration testing platform built with Rails 8. It orchestrates Metasploit modules against network assets, generates structured reports, and provides AI-assisted remediation. The core loop is: **Assets → Scan → Findings → Report → Remediate**.

### Key Features
- **Network scanning**: Metasploit auxiliary modules (safe mode) and exploit modules (exploit mode) run against assets via `ScanService`
- **Agent system**: SSH-tunnel agents deployed to remote sites; each agent heartbeats back and proxies scans through its site's network
- **Exploit sync**: `ExploitSyncJob` walks the local Metasploit module tree and upserts records into the `exploits` table; NVD enrichment (`NvdEnrichmentJob`) then backfills CVSS/CWE data asynchronously
- **AI remediation**: Per-finding remediation advice generated by `OllamaService` (qwen2.5-coder, local); results stored on `findings.ai_remediation`
- **Whitebox code analysis**: File upload → `OllamaService.analyze_code` → structured vulnerability report with PoC
- **Reports**: Generated per scan; exportable as JSON, XLSX, CSV, and whitebox JSON
- **Retest**: Re-runs a prior scan; findings cleared in the retest are auto-marked `remediated` on the original
- **Scan profiles**: Saved exploit selections scoped to an org; picked at scan trigger time
- **Sites**: Logical groupings of assets; agents are assigned to sites and proxy scans for assets in that site
- **REST API**: Full API under `/api/:api_key/...` with key-based auth; mirrors the web UI capabilities
- **Read-only accounts**: Separate account type for view-only access to reports and findings

### Access Levels
- `admin` — full access including scanner, exploit sync, agent management, account control
- regular user — view dashboards, reports, findings, request AI remediation
- read-only account — view reports only (separate `read_only_accounts` table, not `users`)

## Architecture

### App Stack
- **Rails 8.0** — Hotwire (Turbo + Stimulus), ImportMap, Propshaft
- **PostgreSQL 16** — single DB `vulnerability_scanner`, single schema `vuln_scanner`
- **Solid Queue** — background job processor (replaces Sidekiq); jobs: `ScanJob`, `ExploitSyncJob`, `NvdEnrichmentJob`, `DnsLookupJob`
- **Solid Cable** — ActionCable adapter; scan progress broadcast via `Turbo::StreamsChannel`
- **Ollama** — local LLM (qwen2.5-coder) for AI remediation and whitebox code analysis
- **Metasploit** — modules executed via `msfrpcd` (MSGRPC); `msfrpc-client` gem

### Services Layer (`app/services/`)
- `ScanService` — core scan orchestration (threading, MSF console/RPC, finding persistence)
- `OllamaService` — LLM calls: `remediation_for`, `analyze_code`, `generate_secure_version`
- `NvdEnrichmentService` — fetches CVE metadata from the NVD API
- `Aegis::Retester` — retest logic
- `Aegis::WhiteboxPayload` — whitebox report formatting
- `Aegis::ScanLifecycle` / `Aegis::Notifications` — scan start/complete/fail notifications
- `Aegis::ModuleCounter` — counts available MSF modules
- `ScanReportCsv`, `ScanReportXlsx` — report export formatters

### Docker Deployment (Production)
Four services defined in `docker-compose.yml`:

| Service | Image | Notes |
|---------|-------|-------|
| `db` | postgres:16-alpine | Persistent volume; init via `docker/init.sql` |
| `ollama` | ollama/ollama | Persistent model volume; healthcheck waits for qwen2.5-coder |
| `msfrpc` | ubuntu:24.04 | `network_mode: host`; mounts `/opt/metasploit-framework` read-only |
| `rails` | local build | Port 3000; `RUNNING_IN_DOCKER=1`; mounts MSF and `./logs` |

The Rails container connects to msfrpc via `MSF_RPC_HOST=172.20.0.1` (host gateway). SSL is disabled (`MSF_RPC_SSL=false`). All config via `.env` file.

## Test Setup

- ONE database (`vulnerability_scanner`), ONE schema (`vuln_scanner`), for all environments. There is no test database, no test schema, no `vuln_scanner_test`. Never create one.
- Tests are run with `bundle exec rails test` — never tell the user to type `RAILS_ENV=test`.
- `test/test_helper.rb` wraps the entire test run in an outer PostgreSQL transaction. `Minitest.after_run` rolls it back — dev data (users, orgs, etc.) is fully preserved after tests complete.
- Each individual test is also wrapped in a savepoint (`use_transactional_tests = true`, Rails default) — per-test data is cleaned up after each test.
- `parallelize(workers: 1)` must stay set — required for the single-connection outer transaction approach.

### PostgreSQL sequences are NON-transactional
`nextval`/`setval` side-effects persist even if the surrounding transaction rolls back. If stale fixture rows exist from a pre-fix test run, sequence conflicts occur on the next login (`PG::UniqueViolation sessions_pkey`). One-time fix:
```sql
TRUNCATE vuln_scanner.sessions RESTART IDENTITY;
```

### schema.rb `create_schema` is NOT idempotent
Rails auto-generates `create_schema "vuln_scanner"` (no `IF NOT EXISTS`). Never run `db:schema:load` on an existing database — it will fail with `PG::DuplicateSchema`. Use `db:migrate` only for ongoing development.

### Never propose
- A separate test schema or test database
- `schema_search_path` overrides in the test block of `database.yml`
- `RAILS_ENV=test` commands for the user to type manually

## Raw SQL Schema Prefixes

All raw SQL queries must use the explicit `vuln_scanner.` schema prefix (e.g. `vuln_scanner.assets`, `vuln_scanner.findings`). Do **not** rely on the search_path silently resolving unqualified table names — use the prefix everywhere for consistency and to make schema intent explicit.

ActiveRecord model queries (e.g. `Asset.where(...)`) and migration helpers (e.g. `add_column :exploits`) do **not** need the prefix — they use the search_path correctly.

## HTML / CSS

**Never put `display:flex` on a `<form>` element.** Browser UA stylesheets apply special handling to `<form>` that disrupts flex child alignment even when `align-items:center` is set. Always wrap form content in an inner `<div style="display:flex;...">`, or preferably, use a grid instead.
